# EV-01 A — Same-key contention 로컬 측정 보고서 (2026-10-26)

## 판정 및 범위

본 측정 12회(20/50/100/200 VU × 각 3회), HTTP 요청 1,110건에서 correctness 기준을 모두 충족했다. HTTP 실패, 예상 외 업무 상태, JSON 파싱 실패는 각각 0건이며 5,550개 check가 모두 통과했다. 각 run의 Payment attempt/external info/sequence 및 VAN ledger와 TCP 승인 수신은 각각 1건이었다. 이 관측 범위에서 동일 키 승인 멱등성과 외부 호출 단일성을 확인했다. 지연 SLO가 정의되어 있지 않으므로 성능 합격이나 운영 용량 판정은 하지 않는다.

이 문서는 기존 로컬 원본을 읽어 작성했다. 새 부하 테스트, Production 코드/설정 변경, DB 재조회·변경은 수행하지 않았다. 초안 작성 단계에서는 commit/push 없이 검토용으로 남겼으며, 최종 감사 후 보고서와 wrapper 변경만 Git 반영 대상으로 한다.

## 측정 및 집계 방법

`k6/same-key-contention.js`는 `per-vu-iterations`, VU당 1 iteration/HTTP POST, `maxDuration=45s`로 동일 posTrx·금액·카드 payload에 burst를 가한다. 각 run은 서로 다른 posTrx를 사용한다(완료 run 14개 모두 중복 없음). k6 기본 카드는 공개 테스트 카드이지만 당시 EV01_PAN/만료일 override 값은 원본에 저장되지 않아 실제 값은 확정하지 않는다.

분석 대상은 아래 표의 12개 run으로 고정했다. Smoke 여부를 나타내는 별도 필드는 없으므로 요청된 4구간 × 3회 반복 묶음으로 본 측정을 식별하고, 그 밖의 완료된 단일 run 2개를 Smoke Test로 분리했다.

| 제외 run | 분류 | 근거 / 상태 |
|---|---|---|
| `20261026T133636Z-c20-r1` | Smoke Test (20 VU) | 완료 PASS, 요청 20건; 본 측정 c20 r1–r3 이전 단일 run |

Smoke 2회는 교차 검증과 ZIP 보관에는 포함했지만 아래 통계의 분자·분모에서 모두 제외했다. 사전 중단 시도도 통계에서 제외했다.

VU는 동시 가상 사용자 수다. 200 VU는 200 TPS를 의미하지 않으며, 이번 시나리오에서는 동일 키에 각각 한 번씩 요청한 가상 사용자 200명을 뜻한다.

지연은 JSON `metrics.http_req_duration.values`의 `med`(p50), `p(95)`, `p(99)`, `max`(ms)를 사용한다. 이 HTTP 지연은 연결 대기/연결 수립을 포함한 전체 iteration 시간과 다르다. 구간 요약은 run별 percentile의 산술평균이며, 합쳐진 요청의 percentile이 아니다. 개별 요청 시계열이 없어 pooled p95/p99는 계산할 수 없다.

실행시간은 JSON `ev01_test_run_duration_ms`와 `state.testRunDurationMs`가 같은지 확인하고 1000으로 나눴다. `run-summary.txt`의 `wall_clock_seconds`는 wrapper 추출식이 밀리초 정수부만 보존해 최대 0.000999초 작아지므로 보고서 계산에 사용하지 않았다. 아래 표는 소수 셋째 자리로 반올림한다. 요청 처리율은 `요청 수 / k6 실행시간`이며 end-to-end wrapper 소요시간이나 지속 TPS가 아니다.

## 원본 교차 검증

- 본 측정 12회와 Smoke 2회 각각 JSON 요청 수 = iteration 수 = VU 수, APPROVED + PROCESSING = 요청 수, 모든 threshold `ok=true`, HTTP failure rate 0, invalid/unexpected 0을 확인했다. HTTP 실패 metric은 rate metric의 `passes`가 실패 조건 성립 수이므로 `fails` 필드를 HTTP 실패 건수로 잘못 읽지 않았다.
- JSON의 5개 check 각각 passes=VU, fails=0이며 `k6-output.txt`의 요청·업무 상태 요약도 JSON과 일치한다. `run-summary.txt`는 PASS 및 동일 run_id/posTrx/VU인지 확인했다.
- `payment-assertion.txt`: assertion_ok=1, PAYMENT_ATTEMPT=1, PAYMENT_EXTERNAL_INFO=1, PAYMENT_ATTEMPT_SEQ=1 row/LAST_SEQ=1, FINAL_STATUS=APPROVED, approval_no_count=1을 전 run에서 확인했다.
- `van-assertion.txt`: assertion_ok=1, van_approval_count=approved_count=approval_no_count=1을 확인했다. assertion의 posTrx는 환경/summary와 모두 일치한다.
- `van-log-delta.txt`를 다시 세어 정확한 posTrx의 `[van-tcp][approval][received]`=1, attemptSeq=1을 확인하고 `van-log-assertion.txt`의 1과 대조했다. 승인 result 로그도 각 1건/APPROVED였다. VAN ledger 자체의 멱등 처리만으로 중복 호출 부재를 판단하지 않았다.
- 현재 남아 있는 VAN 전체 로그에서 환경 파일의 baseline byte 길이까지 POSIX cksum/line 수를 재계산했고, 그 뒤 prefix가 보관된 각 delta와 일치했다. 당시 inode/rotation fail-fast 실행 결과는 PASS 기록으로 확인하며, 현재 inode만으로 당시 연속성을 별도로 증명하지 않는다.
- DB CSV를 직접 파싱해 event type과 lock_wait_observed의 일치, 비어 있지 않은 행, 유효 시각/비음수 active 수를 확인했다. 완료된 14회 모두 sampler stderr는 비어 있다. DB assertion은 당시 저장된 SQL 결과를 검증한 것이며 현재 DB를 재조회한 것은 아니다.

표는 헤더를 제외한 **관측 행 수**다. sampler는 한 번의 pg_stat_activity 조회에서 active backend별 한 행을 만들며, active가 없을 때도 LEFT JOIN으로 0/빈 event 행 하나를 만든다. 동일 backend가 여러 조회에서 반복될 수 있고 `clock_timestamp()`가 행마다 평가되어 같은 조회의 시각도 달라질 수 있다. 따라서 CSV 행 수나 distinct timestamp 수를 샘플 횟수/고유 연결 수/고유 Lock 사건 수로 취급하지 않는다. active_connection_count도 조회 내 반복된 집계값이므로 합산하지 않았다.

대부분 `Lock/transactionid`이며 `Lock/tuple`도 관측되었다. 코드의 `PaymentAttemptMapper.acquireApprovalSerializationLock`는 동일 POS_TRX에 INSERT ... ON CONFLICT DO UPDATE(no-op)를 수행하고, `ApprovalPrepareTxService.prepare`가 기존 attempt 조회 전에 이를 호출한다. 관측된 transaction/tuple 대기는 이 hot-key 직렬화 설계와 부합한다. VU 증가와 지연 증가도 함께 보이지만 CSV에는 PID, query, blocker, relation/tuple 정보가 없어 모든 wait를 특정 SQL이나 테이블에 확정 귀속할 수 없다.

`LWLock/LockManager`는 sampler의 `wait_event_type=Lock` 기준 boolean에는 false이며 Lock/transactionid와 분리 집계했다. ClientRead와 WalSync 관측도 별도로 남겼다. 최대 active 10은 전체 connection 수나 pool 설정의 직접 증거가 아니다.

설정 간격은 0.25초이나 매 loop가 psql 연결/조회 후 sleep하므로 실제 관측 간격은 더 길고 가변적이다. 짧은 run에서는 관측점이 적으며 sampler 자체의 오버헤드도 있다. 행 수 × 0.25초를 누적 lock wait duration으로 환산하거나 lock 점유율/병목 기여율로 제시하지 않는다.

## 변경 및 검증

`scripts/run-same-key-contention.sh`의 DB sampler 호출 한 줄에 `bash`를 명시했다. 새 checkout에서 sampler가 mode 100644여도 해석기로 실행하도록 하여 사전 중단 원인인 직접 실행 권한 의존성을 제거한다. 기존 작업 트리의 `sample-payment-db-waits.sh` mode 100644 → 100755 변경은 보존했으며 내용은 바꾸지 않았다. Production 소스와 runtime 설정은 변경하지 않았다.

보고서 작성 시 Python 표준 라이브러리로 원본 JSON/SQL 텍스트/CSV/TCP 로그를 교차 검증하고 표를 계산했다. 별도 검증 코드로 보고서의 12개 run, 4개 VU 요약, 12개 wait 행을 원본에서 다시 계산해 모두 일치함을 확인했다. ZIP CRC 및 파일별 SHA-256으로 백업과 원본의 바이트 일치를 확인했다. `bash -n`과 `git diff --check`가 통과했다. sampler의 임시 mode 0644 복사본을 인자 없이 `bash`로 호출해 usage/exit 64까지 도달함을 확인했고 DB 연결은 실행하지 않았다. wrapper는 HEAD 대비 sampler 호출에 `bash`를 추가한 한 줄만 달라졌고, 기존 sampler 내용 및 Git index/HEAD는 유지되었다. 부하 재실행이나 서비스 기동은 하지 않았다.

## 한계 및 후속 해석

한 로컬 머신의 단일 키 짧은 burst를 concurrency별 3회 수행한 결과다. ramp-up/장시간 steady state, 서로 다른 키 분산, 실 VAN, 운영 네트워크, Recovery backlog, 다른 금액/카드/실패 경로를 검증하지 않았다. 측정 순서는 20→50→100→200이며 별도 두 Smoke 외에 통제된 warm-up/캐시·JIT 안정화/순서 무작위화가 없다. 작은 표본의 percentile, run 변동, 로컬 자원 경쟁 및 DEBUG SQL 로깅 영향이 포함될 수 있다.

완료된 12회의 correctness는 충족했으나 최대 TPS, 운영 capacity, 성능 개선 효과 또는 lock 대기의 누적 시간은 이 자료로 결론낼 수 없다. 설정/버전의 누락과 집계 JSON만 남은 한계를 유지한 상태로 A단계 로컬 검증을 마감한다.
