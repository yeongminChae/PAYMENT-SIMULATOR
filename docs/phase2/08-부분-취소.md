# 08. 부분 취소

- 상태: 결정
- 날짜: 2026-11-28
- 플랫폼 근거: ADR-0032 (v1은 전체 반품 + 재판매, 유지), backlog "부분 반품" (Retail-Platform)
- 해소하는 차이: D17 (`00-플랫폼-차이.md`)

## 요점

- **원승인 하나를 남은 금액이 있는 한 여러 번 나눠 취소한다.** 취소 합계는 원승인 금액을 넘을 수 없다. 남은 금액이 0이면 전액 취소와 같다.
- **범위는 Payment · VAN Simulator 기능까지.** 플랫폼 부분 반품(POS 화면, 라인별 부가세, 복합결제 환불 순서)은 backlog에 그대로 둔다. v1 POS는 지금처럼 전액만 취소한다.
- **핵심 난이도는 "동시에 들어온 취소가 합계를 넘지 않게"와 "결과를 모르는 취소의 금액을 어떻게 셀까"다.** 이 부분은 직접 구현한다 (5장).

```text
원승인 30,000원
 ├ 1차 부분 취소 10,000원 → 남은 금액 20,000원
 └ 2차 부분 취소 20,000원 → 남은 금액 0원 (= 전액 취소)
```

## 1. 규칙

| 규칙 | 내용 |
|---|---|
| 대상 | `APPROVED` 승인. 망취소된 승인은 대상 아님 (망취소는 결과 불명 승인만, 전액) |
| 금액 | 1원 이상, 남은 금액 이하. 원 단위 정수 (ADR-0016) |
| 남은 금액 | 원승인 금액 − 성공한 취소 합계 − **진행 중 취소 합계** |
| 진행 중 취소 | 한 원승인에 동시에 **1건만** (`PENDING` · `UNKNOWN_TIMEOUT`). 끝나야 다음 취소를 받는다 → `CANCEL_IN_PROGRESS` |
| 거절된 취소 | 금액에 세지 않는다 (04 4장) |
| 망취소와의 관계 | 성공한 취소가 하나라도 있으면 망취소 불가, 망취소 성공이면 취소 불가 (DESIGN.md 6장 불변식을 "취소 합계 > 0"으로 넓힘) |
| 운영 취소 (04) | 금액 = 남은 금액 전부 |

### 1.1 결과를 모르는 취소의 금액

- 응답이 없어 `UNKNOWN_TIMEOUT`인 취소는 **실제로 됐을 수도 있다.** 그래서 남은 금액 계산에서 **이미 취소된 것처럼 뺀다**(예약). 그래야 그 사이 다른 취소가 합계를 넘기지 않는다.
- Recovery · 조회로 `CANCELLED`가 되면 예약이 확정되고, `CANCEL_DECLINED`가 되면 예약이 풀린다.

### 1.2 재시도 규칙 (POS_APP 쪽에 알려야 할 것)

- 같은 취소를 다시 보낼 때는 **반드시 같은 취소 posTrx**로 보낸다. 같은 posTrx면 멱등으로 저장된 결과를 돌려준다.
- 새 posTrx로 보내면 Payment는 **새 부분 취소**로 본다. 결과 불명 뒤 새 posTrx로 다시 보내면 두 번 취소될 수 있다. 진행 중 1건 규칙이 대부분 막지만, 앞 취소가 확정된 뒤에는 막을 수 없다.
- 승인 재결제(ADR-0045: 결과 불명 뒤 새 결제순번)와 **반대 규칙**이다. 플랫폼 부분 반품을 설계할 때 Retail-Platform ADR로 옮긴다. v1 전액 취소에서는 남은 금액이 0이 되어 두 번째가 `ALREADY_CANCELLED`로 막힌다.

## 2. 저장 · 불변식

DB 제약을 최종 기준으로 둔다 (DESIGN.md 7.2와 같은 원칙).

| 위치 | 바꿈 |
|---|---|
| `PAYMENT_ATTEMPT` | `CANCELLED_AMOUNT` · `RESERVED_AMOUNT` 컬럼 추가. `CHECK (CANCELLED_AMOUNT + RESERVED_AMOUNT <= AMOUNT)` |
| `PAYMENT_CANCEL` | `AMOUNT` 컬럼 추가 (`CHECK > 0`). 04의 부분 유니크를 `WHERE CANCEL_STATUS IN ('PENDING', 'UNKNOWN_TIMEOUT')`로 좁힘 → 진행 중 1건 |
| VAN Simulator `van_approval` · `van_cancel` | 같은 컬럼 · 제약 · 부분 유니크 |

**상태 전이와 금액**

| 취소 전이 | `RESERVED_AMOUNT` | `CANCELLED_AMOUNT` |
|---|---|---|
| 새 취소 `PENDING` 저장 (TX1) | + 금액 | — |
| `CANCELLED` 확정 (TX2 · Recovery · 운영 확정) | − 금액 | + 금액 |
| `CANCEL_DECLINED` 확정 | − 금액 | — |
| `UNKNOWN_TIMEOUT` | 그대로 (예약 유지) | — |

- 금액 갱신은 취소 상태를 바꾸는 **같은 조건부 UPDATE 트랜잭션** 안에서 한다. 상태만 바뀌고 금액이 안 바뀌는 일이 없게 한다.
- TX1은 원승인 행을 잠근 뒤(기존 직렬화) 남은 금액을 다시 계산하고 예약한다. 잠금은 직렬화일 뿐이고, 초과는 `CHECK`가 최종으로 막는다 (DESIGN.md 6장 교훈: 직렬화 ≠ 불변식 보장).

## 3. 합산 상태 · 매입 · 조회

- **합산 (02):** 빠진 금액 = 원승인 금액 − `CANCELLED_AMOUNT`. 남은 금액 > 0이면 빠짐, 0이면 안 빠짐, 진행 중 취소가 있으면 미확정. 메시지 `cancels[]`에 건별 금액을 싣는다.
- **매입 (07):**
  - 매입 전 부분 취소 → 매입 금액 = 남은 금액. 남은 금액 0이면 매입 대상 아님.
  - 매입 후 부분 취소 → VAN에서 **부분 매입 취소**로 처리하고(시뮬레이터 규칙, 가정), 매입 결과 메시지에 취소 금액을 싣는다.
- **운영 조회 (03):** 원승인별 취소 합계 · 예약 금액 · 남은 금액을 보여 준다.

## 4. API

- `/cancel` 요청에 `amount`(선택)를 추가한다. 없으면 남은 금액 전부(지금 동작과 같음).
- 응답에 `cancelledAmount` · `remainingAmount`를 추가한다.
- 새 오류: `CANCEL_AMOUNT_EXCEEDED`(남은 금액 초과), `CANCEL_IN_PROGRESS`(진행 중 취소 있음).

## 5. 직접 구현 / AI에 맡길 것

| 직접 (어려움) | 왜 어려운가 |
|---|---|
| 남은 금액 예약 · 확정 · 해제 (2장 표) | 상태와 금액이 한 트랜잭션에서 같이 움직여야 하고, Recovery · 운영 확정 · 사람 조회 세 경로가 모두 같은 규칙을 지켜야 함 |
| 동시 부분 취소 경합 | 같은 원승인에 동시 취소 N건 → 성공 합계 ≤ 원승인 금액, 진행 중 1건. 잠금 + `CHECK` + 부분 유니크 조합 |
| 취소 vs 망취소 불변식 확장 | "성공 1건"이 "취소 합계 > 0"으로 바뀜. 반대편 원장 재확인 로직 수정 |
| 결과 불명 부분 취소의 Recovery | 예약을 유지한 채 조회로 확정, update miss 시 재조회 후 금액 정합성 확인 |
| VAN Simulator 같은 불변식 | Payment를 믿지 않고 VAN도 독립적으로 합계를 막음 |

| AI에 맡겨도 됨 (반복 · 정형) |
|---|
| DTO · API 필드 추가 (`amount`, `cancelledAmount`, `remainingAmount`), 오류 코드 |
| 스키마 컬럼 추가 · 마이그레이션 |
| 합산 상태 · 운영 조회 · 매입 결과 메시지의 금액 표시 |
| VAN 전문 필드 추가, 전문 문서 갱신 |
| 테스트 픽스처 · 단위 테스트 뼈대 (경합 테스트 시나리오 설계는 직접) |

4. API · 합산 · 매입 · 운영 조회 반영
5. 테스트
   - 30,000원 승인에 10,000원 부분 취소 동시 5건 → 성공 3건, 나머지 `CANCEL_AMOUNT_EXCEEDED` 또는 `CANCEL_IN_PROGRESS`, 합계 30,000원
   - 부분 취소 결과 불명 중 다른 취소 → `CANCEL_IN_PROGRESS`, Recovery가 `CANCELLED` · `CANCEL_DECLINED`로 확정하면 예약 확정 · 해제
   - 같은 취소 posTrx 재요청 → 멱등, 다른 금액 → `CONFLICT`
   - 부분 취소 성공 뒤 망취소 → 거부
   - 매입 전 부분 취소 → 매입 금액 = 남은 금액
