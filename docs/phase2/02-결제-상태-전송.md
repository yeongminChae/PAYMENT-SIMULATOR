# 02. 결제 상태 아웃박스 전송

- 상태: 결정
- 날짜: 2026-11-26
- 플랫폼 근거: ADR-0025, ADR-0043, ADR-0045 (Retail-Platform)
- 해소하는 차이: D7 (`00-플랫폼-차이.md`)

## 1. 합산 상태 (posTrx별)

판단 기준은 ADR-0025 그대로다: **"고객 돈이 지금 빠져 있는가"**.

### 1.1 승인 시도 하나의 판정

| 원승인 `FINAL_STATUS` | 그 승인의 취소 · 망취소 | 판정 |
|---|---|---|
| `DECLINED` | — | 안 빠짐 |
| `APPROVED` | 없음, 또는 `CANCEL_DECLINED` · `REVERSAL_DECLINED`만 | **빠짐** |
| `APPROVED` | `CANCELLED` 또는 `REVERSED` | 안 빠짐 |
| `APPROVED` | 취소 `PENDING` · `UNKNOWN_TIMEOUT`, 망취소 `PENDING` | 미확정 |
| `UNKNOWN_TIMEOUT` · `PROCESSING`(NULL) | `REVERSED` 또는 `CANCELLED` | 안 빠짐 |
| `UNKNOWN_TIMEOUT` · `PROCESSING`(NULL) | 그 밖 | 미확정 |

- 망취소 성공 뒤 Recovery가 원승인을 `APPROVED`로 확정해도 판정은 "안 빠짐"이다 (ADR-0021 맥락).
- 취소 + 망취소 성공은 원승인당 최대 1건이다 (DESIGN.md 6장).

### 1.2 posTrx의 판정

- 시도 중 하나라도 **미확정**이면 posTrx는 **미확정**
- 아니면 하나라도 **빠짐**이면 **빠짐**
- 아니면 **안 빠짐**

미확정이어도 이미 빠짐으로 확정된 승인은 빠진 금액 · 목록에 넣는다. 빠진 승인이 2건 이상이면 이중 결제다 (ADR-0025). posTrx 규칙(ADR-0045)상 이 경우는 `DECLINED` 뒤 같은 posTrx 재시도에서만 생긴다.

### 1.3 고객 반품 취소의 귀속

반품 카드 취소는 **원승인의 posTrx 상태에 포함**한다. 반품 posTrx로는 따로 보내지 않는다.

- 두 레포의 현재 구조와 같다: POS_APP 반품은 새 거래 키 + 원거래 연결(`origStrCd · origPosNo · origTranNo`), Payment `/cancel`은 `posTrx`(반품) + `originalPosTrx · originalAttemptSeq`.
- 원승인 posTrx의 상태가 "빠짐 → 안 빠짐"으로 바뀌고, 메시지의 `cancels[]`에 반품 posTrx · 금액 · 일시가 들어간다. ERP는 반품 posTrx로 반품 판매를 찾는다.
- 운영 취소(04)도 같은 방식으로 원승인 posTrx에 포함하고 `kind = OPERATION`으로 구분한다.

## 2. 언제 기록하나

결과가 정해지는 순간에만 기록한다. 기록은 그 상태를 바꾼 **같은 트랜잭션**에서 한다.

| 계기 | 트랜잭션 | 대상 posTrx |
|---|---|---|
| 승인 결과 반영 (`APPROVED` · `DECLINED` · `UNKNOWN_TIMEOUT`) | 승인 TX2 | 승인 posTrx |
| 사람의 승인 조회로 확정 (`/inquiry`) | 조회 확정 TX | 승인 posTrx |
| 취소 결과 반영 · 취소 조회 확정 | 취소 TX2 · 조회 TX | **원승인** posTrx |
| 망취소 결과 반영 | 망취소 TX2 | **원승인** posTrx |
| Recovery 확정 (승인 · 취소 · 망취소) | Target Ledger Finalization TX | 원승인 posTrx |
| `MANUAL_REVIEW` 전환 · 재대기로 해제 | TX-R2 · 재대기 TX | Task의 `ORIGINAL_POS_TRX` |
| 운영 확정 · 운영 취소 (04) | 04에서 정함 | 원승인 posTrx |

기록하지 않는 것:
- 승인 · 취소 · 망취소를 **막 만든 시점**(`PROCESSING` · `PENDING`). 정상 거래는 몇 초 안에 끝나므로 잠깐 "미확정"이 나갔다 바뀌는 일을 만들지 않는다. 오래 멈춘 건은 Recovery가 확정하거나 `MANUAL_REVIEW`로 보낼 때 기록된다.
- request-not-sent 정리(승인 시도 삭제). 아무 일도 없었던 것이다.
- 결과가 같은 재응답(멱등 재요청, `ALREADY_CANCELLED` 등).

## 3. 저장

### 3.1 `PAYMENT_TRX_STATUS` — 합산 상태 (영구)

| 컬럼 | 설명 |
|---|---|
| `POS_TRX` (PK) | |
| `VERSION` | posTrx별 변경 순번. 1부터, 변경마다 +1 |
| `STATUS` | `CHARGED`(빠짐) / `NOT_CHARGED`(안 빠짐) / `UNRESOLVED`(미확정) |
| `CHARGED_AMOUNT` | 빠진 금액 합 |
| `MANUAL_REVIEW` | 이 posTrx에 걸린 `MANUAL_REVIEW` Task가 있는가 |
| `SNAPSHOT` | 전송 메시지 본문 (JSON, 4장) |
| `UPDATED_AT` | |

- 버전은 아웃박스가 지워져도 이어져야 하므로 아웃박스와 따로 둔다. 운영 조회(03)도 이 테이블을 읽는다.
- **직렬화:** 계기 트랜잭션은 원장을 바꾼 뒤 `PAYMENT_TRX_STATUS` 행을 `INSERT … ON CONFLICT DO NOTHING` → `SELECT … FOR UPDATE`로 잠그고, 그 posTrx의 원장을 다시 읽어 합산 · 버전 증가 · 저장한다. 같은 posTrx의 계기(예: 반품 취소와 Recovery 확정)가 겹쳐도 버전이 꼬이지 않는다.
- 합산 결과가 직전과 같으면(예: `MANUAL_REVIEW` 해제 후에도 미확정 유지) 버전을 올리고 기록한다. `MANUAL_REVIEW` 여부도 메시지 내용이기 때문이다. 원장 · Task 변화가 전혀 없는 재응답은 2장대로 기록하지 않는다.

### 3.2 `PAYMENT_STATUS_OUTBOX` — 보낼 목록

| 컬럼 | 설명 |
|---|---|
| `ID` (PK) | |
| `POS_TRX` | |
| `VERSION` | 보낼 버전 |
| `SEND_STATUS` | `PENDING` / `SENT` / `QUARANTINED` |
| `ATTEMPT_COUNT` · `NEXT_ATTEMPT_AT` · `LAST_ERROR` | 재시도 |
| `CREATED_AT` · `SENT_AT` | |

- **posTrx당 `PENDING`은 1행**이다 (`UNIQUE (POS_TRX) WHERE SEND_STATUS = 'PENDING'`). 새 버전이 생기면 그 행의 `VERSION`만 올린다. 전송 때는 `PAYMENT_TRX_STATUS`의 최신 `SNAPSHOT`을 보낸다 → 5분 사이 여러 번 바뀌어도 **최신 1건만** 나간다. 중간 이력은 `PAYMENT_EVENT_LOG`에 있다.
- 전송 완료는 `SENT`로 바꾸고 **7일 뒤 삭제**한다 (하루 1회 정리 작업). 일 대사(T+1)와 주말 장애 조사를 덮는 기간이다.
- `QUARANTINED`는 자동 삭제하지 않는다.

## 4. 메시지 (계약 초안)

계약 원본은 Retail-Platform `contracts/`에 둔다 (ADR-0025). 아래는 초안이다.

```json
{
  "contractVersion": "1",
  "posTrx": "2301-20261126-0003-0042-01",
  "version": 3,
  "status": "NOT_CHARGED",
  "chargedAmount": 0,
  "chargedApprovals": [],
  "approvals": [
    { "attemptSeq": 1, "finalStatus": "APPROVED", "amount": 15000,
      "approvalNo": "12345678", "approvedAt": "2026-11-26T10:00:01+09:00" }
  ],
  "cancels": [
    { "kind": "CUSTOMER", "cancelPosTrx": "2301-20261126-0001-0007-01",
      "originalAttemptSeq": 1, "amount": 15000, "cancelStatus": "CANCELLED",
      "cancelledAt": "2026-11-26T15:20:00+09:00" }
  ],
  "reversals": [],
  "unresolved": [],
  "manualReview": false,
  "changedAt": "2026-11-26T15:20:00+09:00"
}
```

- `chargedApprovals[]`: 빠진 승인 (`attemptSeq` · `approvalNo` · `amount`). 2건 이상이면 이중 결제.
- `unresolved[]`: 미확정 건 (`type` = `APPROVAL` / `CANCEL` / `REVERSAL`, 대상 posTrx, 시도 순번, 현재 상태).
- 카드 정보는 보내지 않는다 (ADR-0006). 금액은 원 단위 정수 (ADR-0016).
- 일시는 `+09:00` 오프셋을 붙인 ISO-8601.

## 5. 전송

| 항목 | 값 |
|---|---|
| 주기 | 5분 (`payment.status-push.interval`, 기본 `5m`) — ADR-0025 |
| 대상 | 설정 `payment.status-push.target-url`. "ERP 전용"이 아니라 범용 "결제 상태 전송" (ADR-0025) |
| 켜기 | `payment.status-push.enabled` (기본 `false`, 플랫폼 실행 환경에서 켬) |
| 묶음 | 한 번에 최대 100건, ERP는 건별 결과 반환 (ADR-0043) |
| 순서 | 만든 순서대로 시도하되 한 건이 막혀도 다음 건 진행. 순서 보장 안 함 (ADR-0043) |

### 5.1 한 번의 실행

1. `PENDING`이고 `NEXT_ATTEMPT_AT`이 지난 행을 최대 100건 `FOR UPDATE SKIP LOCKED`로 가져와(여러 인스턴스 대비) 각 행의 `VERSION`과 최신 `SNAPSHOT`을 읽고 커밋한다.
2. 트랜잭션 밖에서 HTTPS로 보낸다.
3. 건별 결과를 반영한다.

| 결과 | 처리 |
|---|---|
| 수신 성공 · 이미 받음(멱등) · 낮은 버전 무시 | `VERSION`이 1에서 읽은 값과 같을 때만 `SENT`. 그 사이 버전이 올랐으면 `PENDING` 유지 → 다음 실행에 최신 버전 전송 |
| 거부 (읽을 수 없음 · 필수 값 없음 · 지원하지 않는 계약 버전) | `QUARANTINED` + 즉시 알림. 같은 posTrx의 이후 변경은 새 `PENDING` 행으로 쌓인다 |
| 네트워크 오류 · 응답 없음 · 5xx | `ATTEMPT_COUNT`+1, `NEXT_ATTEMPT_AT` = 1초 → 2초 → 4초 … 최대 5분. 포기하지 않는다 |

- 응답이 없으면 ERP가 받았는지 모르지만 다시 보내도 안전하다 (ERP 멱등 · 버전 비교).
- 격리 건은 원인을 고친 뒤 전산 담당자가 재전송한다 (관리 API, 05에서 정함).

### 5.2 알림 · 지표

ADR-0043: 가장 오래된 미전송 건이 **30분**을 넘으면 알림, 격리는 **즉시** 알림, 미전송 건수 · 가장 오래된 대기 시간을 지표로. 채널 · 지표 구현은 05에서 정한다.

## 6. 미정

- ERP ↔ Payment 시스템 간 인증 방식 — `contracts/` 작성 때 플랫폼에서 정한다.
- 계약 버전 규칙(호환 범위) — ADR-0043 후속, `contracts/` 작성 때.
