# 07. 매입 · 정산

- 상태: 결정
- 날짜: 2026-11-28
- 플랫폼 근거: ADR-0027, ADR-0040, ADR-0048, ADR-0049 (Retail-Platform)
- 해소하는 차이: D16 (`00-플랫폼-차이.md`)

## 요점

- **승인 = 찜, 매입 = 청구.** 매입(카드사에 대금 청구)을 해야 고객 돈이 실제로 나가고 가게에 입금된다. 매입하지 않은 승인은 며칠 뒤 풀린다 (가정).
- **매입은 ERP 일 대사가 끝난 점포 · 영업일만, 하루 1회 보낸다.** 판매에 안 쓴 승인은 ERP의 **매입 제외 목록**으로 빼고 청구한다.
- **뺀 승인은 자동 취소하지 않는다.** 고객 돈은 나가지 않는다. 고객이 문의하면 담당자가 운영 취소한다 (ADR-0040).
- **분담:** 매입은 Payment(VAN 경유), 정산 대사 · 회계(입금 ↔ 매입, 수수료, 미수금)는 ERP. Payment는 매입 결과를 ERP에 보낸다.

## 1. 흐름 (가정 포함)

```text
D일     승인 (찜)                      Payment 원장
D일 밤  점포 마감 → ERP 일 대사 (T+1)   ERP: 판매에 안 쓴 승인 = 매입 제외 목록
D+1     Payment ─ "그 점포 · 영업일 제외 목록 준비됐어?" ─▶ ERP
        Payment ─ 매입 요청 (가맹점 · 영업일 단위) ─▶ VAN ─▶ 카드사
        VAN ─ 건별 결과: 매입 확정(수수료 · 입금 예정일) / 반송 ─▶ Payment
        Payment ─ 매입 결과 (아웃박스, 5분) ─▶ ERP
D+2~    카드사 입금 (수수료 뺀 금액)     ERP 정산 대사: 입금 ↔ 매입 확정
```

- 실제 매입 주기 · 입금 일정은 카드사 · VAN 계약마다 다르다 (가정). 시뮬레이터에서는 VAN Simulator 설정값으로 둔다.

## 2. 매입 대상

ERP 대사가 끝난 **점포 · 영업일**(posTrx 날짜 자리) 단위로 고른다.

| 승인 상태 | 매입 |
|---|---|
| `APPROVED`, 성공 · 진행 중 취소 · 망취소 없음, 제외 목록에 없음 | **포함** |
| 제외 목록에 있음 (판매에 안 쓴 승인) | **제외**, 자동 취소 없음 |
| 취소 · 망취소 성공 | 대상 아님 |
| 미확정 (`UNKNOWN_TIMEOUT` · `MANUAL_REVIEW` 등) | 보류. 확정되면 다음 매입 회차에 **이월 매입** |
| 이미 매입됨 | 대상 아님 (같은 승인은 한 번만) |

- 운영 취소 posTrx(운영 전용 POS, ADR-0047)는 승인이 아니므로 대상이 아니다.

## 3. ERP 매입 제외 목록 (ADR-0049)

- Payment가 매일 05:00부터 30분마다, 아직 매입하지 않은 점포 · 영업일에 대해 ERP에 묻는다 (Payment → ERP).
- ERP 응답: `ready`(대사 완료 여부), `excluded[]`(posTrx · attemptSeq).
  - `ready = false`면 그 점포 · 영업일은 다음 회차에 다시 묻는다. 점포가 마감하지 않으면 대사가 안 끝나므로 매입도 늦어진다 (입금 지연).
  - 3일 넘게 준비되지 않으면 알림 (05).
- 제외 목록에 Payment가 모르는 승인이 있으면 무시하고 경고 로그를 남긴다.

## 4. 매입 요청 · 결과

- **매입 묶음:** 가맹점 × 영업일 하나가 VAN 매입 요청 하나다 (`ACQUISITION_BATCH`). 가맹점은 승인에 저장된 `MERCHANT_ID` (06).
- **VAN 전문 `ACQUISITION`:** 묶음 번호, 가맹점 ID, 건별(posTrx · attemptSeq · 승인번호 · VAN 거래번호 · 터미널 ID · 금액).
- **건별 결과:**
  - `ACCEPTED`: 수수료 · 입금 예정일
  - `RETURNED`: 반송 사유 (예: 승인 없음, 이미 매입됨, 취소된 승인)
- **멱등:** 묶음 번호가 같으면 VAN은 저장된 결과를 다시 준다. 응답이 없으면 같은 묶음 번호로 다시 보낸다. 승인 · 취소와 달리 매입 요청은 재전송해도 안전하게 만든다 (VAN이 묶음 번호로 중복을 막음).
- **반송:** 알림(05)과 함께 ERP에 결과로 보낸다. 재매입 여부는 담당자가 판단한다 (재매입 운영 요청은 미정).

## 5. 매입 뒤에 일어나는 일

| 일 | 처리 |
|---|---|
| 매입된 승인의 고객 반품 취소 | 기존 취소 그대로. VAN은 매입된 승인의 취소를 **매입 취소**로 처리한다 (시뮬레이터 규칙, 가정). 매입 결과 메시지에 `CANCELLED_AFTER_ACQUISITION`으로 알린다 |
| 제외된 승인을 고객이 문의 | 담당자가 ERP에서 운영 취소 (ADR-0040) |
| 대사가 늦게 맞아 "판매에 쓰인 승인"이 제외됐던 경우 | 다음 회차 제외 목록에서 빠지면 이월 매입으로 포함 |

## 6. ERP로 보내는 매입 결과 (계약 초안)

결제 상태 · 종료 신호와 같은 5분 아웃박스로 보낸다 (02 규칙).

```json
{
  "contractVersion": "1",
  "posTrx": "1000-20261126-0001-0199-01",
  "attemptSeq": 1,
  "merchantId": "00987654321",
  "batchId": "ACQ-00987654321-20261126",
  "result": "ACCEPTED",
  "amount": 15000,
  "fee": 225,
  "payoutDate": "2026-11-30",
  "returnReason": null
}
```

- `result`: `INCLUDED`(요청함) / `EXCLUDED`(제외) / `ACCEPTED` / `RETURNED` / `CANCELLED_AFTER_ACQUISITION`.
- ERP는 이걸로 정산 대사(입금 예정 ↔ 실제 입금)와 수수료 회계를 한다.

## 7. 저장

| 테이블 | 내용 |
|---|---|
| `ACQUISITION_DAY` | 점포 · 영업일별 진행 상태 (`WAITING_ERP` / `REQUESTED` / `DONE`), 제외 목록 수신 일시 |
| `ACQUISITION_BATCH` | 묶음 번호 · 가맹점 · 영업일 · 상태 · 요청 · 응답 일시 |
| `ACQUISITION_ITEM` | posTrx · attemptSeq · 묶음 · 상태(`INCLUDED` / `EXCLUDED` / `ACCEPTED` / `RETURNED` / `CANCELLED_AFTER_ACQUISITION`) · 수수료 · 입금 예정일 · 반송 사유 (`UNIQUE (POS_TRX, ATTEMPT_SEQ)` 중 매입된 건) |
| `ACQUISITION_RESULT_OUTBOX` | ERP로 보낼 매입 결과 |

## 8. 미정

- 실제 입금 데이터(카드사 → 가맹점 계좌)를 누가 어떻게 ERP에 넣는지 — 시뮬레이터 범위 밖. ERP 정산 설계 때 정한다.
- 반송 건의 재매입 절차.
- 수수료율 기준(카드사별 · 가맹점별) — VAN Simulator 설정값으로 두고, 실제 계약 구조는 미확인.

## 9. 구현 작업

1. 매입 대상 선정 · `ACQUISITION_*` 테이블
2. ERP 제외 목록 클라이언트 · 05:00부터 30분 폴링 · 3일 알림
3. VAN 전문 `ACQUISITION` · VAN Simulator 매입 원장 · 수수료 · 입금 예정일 · 반송 시나리오 · 매입 후 취소
4. 매입 결과 아웃박스 · 전송
5. 테스트: 제외 목록 건은 매입 안 됨, 대사 미완료 점포는 대기, 미확정 건 이월 매입, 같은 묶음 재전송 시 중복 매입 없음, 매입 후 반품 취소, 반송 알림
