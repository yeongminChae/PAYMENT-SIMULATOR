# 04. 운영 요청 수집 · 검증 · 실행

- 상태: 결정
- 날짜: 2026-11-26
- 플랫폼 근거: ADR-0040, ADR-0047 (Retail-Platform)
- 해소하는 차이: D4 · D5 · D6 · D9 · D10 (`00-플랫폼-차이.md`)

## 요점

- **운영 요청 = 판매와 무관한 결제 정정.** 반품이 아니다. 매출 · 재고는 바뀌지 않는다.
  - 운영 취소: 돈은 빠졌는데 판매에 안 쓰인 승인을 카드 없이 환불 (예: 이중 결제)
  - 운영 확정: 결과를 모르는 건을 담당자가 전화로 확인한 결과로 확정
  - 고객이 상품을 돌려주는 반품은 고객센터 POS에서 카드로 한다 (ADR-0031)
- **Payment ↔ ERP 5분 통신 세 가지** (모두 Payment가 먼저 건다. 서버 핑은 없음)
  1. 운영 요청 가져오기 (`GET`, 폴링): ERP가 대기 중인 작업 지시 목록을 돌려줌
  2. 결제 상태 보내기 (`POST`): posTrx별 합산 상태 (02)
  3. 종료 신호 보내기 (`POST`): 처리한 요청의 결과. 받은 요청은 ERP 대기에서 빠진다. 없으면 1에서 같은 요청이 계속 나온다

## 1. 흐름

```text
담당자 ─ ERP 화면: 운영 요청 입력 ─▶ ERP DB (대기)
Payment ─ 5분마다 "내 운영 요청?" ─▶ ERP                 (Payment가 묻는 방향, ADR-0024)
Payment ─ OPS_REQUEST에 저장 (ERP 요청 ID 유니크 → 다시 가져와도 한 번만)
        ─ 자기 데이터로 검증 → 운영 확정 / 운영 취소(VAN) 실행
        ─ 같은 트랜잭션: 원장 · 합산 상태 · 아웃박스(02) · 감사 로그 · 종료 신호 아웃박스
Payment ─ 5분 전송 ─▶ ERP: 결제 상태(02) + 운영 요청 종료 신호
ERP     ─ 종료 신호를 받은 요청을 대기에서 뺌. 판단은 결제 최종 상태로
```

- 수집 주기 5분 (`payment.ops-request.poll-interval`, 기본 `5m`). 켜기 `payment.ops-request.enabled` (기본 `false`).
- 한 번에 최대 100건, ERP 요청 시각 순서로 처리한다.
- 같은 요청을 다시 받으면(종료 신호가 아직 ERP에 안 닿음) `OPS_REQUEST`에 이미 있으므로 실행하지 않고, 저장된 결과로 종료 신호를 다시 낸다.

## 2. 요청 종류와 입력

| 종류 | 대상 | ERP가 보내는 값 |
|---|---|---|
| 운영 확정 `CONFIRM` | `MANUAL_REVIEW`인 승인 · 취소 · 망취소 | 대상(`targetType` · posTrx · attemptSeq 또는 취소 · 망취소 posTrx), 확인 결과, 근거(문의처 · 일시), 요청자 사번, 사유 |
| 운영 취소 `CANCEL` | 돈이 빠졌지만 판매에 쓰이지 않은 승인 (ERP 판단) | 원승인 posTrx · attemptSeq · 금액, 요청자 사번, 사유 |

### 2.1 운영 확정의 확인 결과

| 대상 | 결과 | 필수 값 |
|---|---|---|
| 승인 | `APPROVED` | **승인번호 · VAN 거래번호 · 금액**(원승인 금액과 같아야 함) |
| 승인 | `DECLINED` | — |
| 취소 | `CANCELLED` | 취소 승인번호 |
| 취소 | `CANCEL_DECLINED` | — |
| 망취소 | `REVERSED` / `REVERSAL_DECLINED` | — |

- 승인번호 · VAN 거래번호가 있어야 나중에 운영 취소(VAN 취소 전문에 원승인 정보가 들어감)와 매입(07)을 할 수 있다. 담당자가 VAN에 확인할 때 함께 받는다고 본다 (**가정**).

## 3. 검증 · 실행

### 3.1 운영 확정

**검증**
- 대상 원장이 아직 미확정이다 (승인 `PROCESSING` · `UNKNOWN_TIMEOUT`, 취소 `PENDING` · `UNKNOWN_TIMEOUT`, 망취소 `PENDING`).
- 대상 Recovery Task가 `MANUAL_REVIEW`다. 재대기로 다시 돌고 있으면(`PENDING` · `RUNNING` · `RETRY_WAIT`) 이번 회차는 건너뛰고 다음 수집 때 다시 본다.
- 필수 값이 있고 금액이 맞는다.

**실행** (VAN 호출 없음, 한 트랜잭션)
1. 원장을 조건부로 확정한다 (Recovery 확정과 같은 조건부 UPDATE, 반영 경로 `OPERATION`).
2. Recovery Task를 `RESOLVED`로, History에 `OPERATOR_CONFIRMED`를 남긴다.
3. 합산 상태 · 결제 상태 아웃박스(02), 감사 로그, 종료 신호 아웃박스.

**이미 확정돼 있으면** (그 사이 Recovery가 확정한 경우)
- 같은 결과 → 종료 `DONE` / `ALREADY_CONSISTENT`
- 다른 결과 → 종료 `CLOSED_NO_CHANGE` / `TERMINAL_CONFLICT` + 즉시 알림 (05). 사람이 확인한 사실과 VAN 기록이 다르므로 다시 확인해야 한다.

### 3.2 운영 취소

**검증** (ADR-0040)
- 원승인이 `APPROVED`이고, 그 승인에 성공했거나 진행 중인 취소 · 망취소가 없다. 거절된 취소(`CANCEL_DECLINED`)만 있는 것은 허용한다 (4장).
- 금액 = 원승인 금액 (전체 취소만. 부분 취소는 08).
- 원승인에 승인번호 · VAN 거래번호가 있다.
- 카드번호는 받지 않는다. 카드 일치 검사(`CancelCardVerificationPolicy`)를 거치지 않는 별도 입구다.

**취소 posTrx** (ADR-0047)

```text
점포(4)-실행일(8)-9999-거래번호(4)-01
예) 1000-20261126-9999-0001-01
```

- 점포는 원승인 posTrx 앞 4자리, 실행일은 Payment 실행 날짜(Asia/Seoul). 영업일은 Retail-POS 소유라 Payment가 모르므로 달력 날짜를 쓴다.
- 9999는 점포마다 ERP에 등록된 **운영 전용 POS** 번호다. 설정값 `payment.ops.pos-no`(기본 `9999`).
- 거래번호는 Payment가 `(점포, 실행일)`별 시퀀스로 매긴다 → `OPS_POS_TRX_SEQUENCE`. 01에서 제거하는 `POS_TRX_SEQUENCE`와는 별개의 운영 취소 전용 테이블이다.
- 번호는 TX1에서 `OPS_REQUEST`에 묶어 저장한다. 같은 요청은 같은 번호를 쓴다.
- 결제순번은 항상 `01`.

**실행** (기존 취소의 TX1 → VAN → TX2 구조 재사용)
1. TX1: 검증 → 취소 posTrx 발급 → `PAYMENT_CANCEL` `PENDING` (`CANCEL_KIND = OPERATION`, `OPS_REQUEST_ID`) → 감사 로그
2. VAN 취소 (원승인 정보로, 카드번호 없음)
3. TX2: 결과 반영 → 합산 상태 · 결제 상태 아웃박스 → 종료 신호

| VAN 결과 | 종료 신호 |
|---|---|
| `CANCELLED` | `DONE` |
| `CANCEL_DECLINED` | `CLOSED_NO_CHANGE` / `VAN_DECLINED` |
| 응답 없음 (`UNKNOWN_TIMEOUT`) | 아직 안 보냄. Recovery가 취소를 확정하면 그 트랜잭션에서 위 표대로 보냄. `MANUAL_REVIEW`가 되면 운영 확정으로 이어짐 |

### 3.3 검증 실패 (종료 `CLOSED_NO_CHANGE`)

| reasonCode | 뜻 |
|---|---|
| `TARGET_NOT_FOUND` | 대상 거래 없음 |
| `NOT_UNRESOLVED` | 운영 확정 대상이 이미 확정됨 (결과가 같으면 `DONE` / `ALREADY_CONSISTENT`) |
| `TERMINAL_CONFLICT` | 확정 결과가 저장된 결과와 다름 |
| `NOT_APPROVED` | 운영 취소 대상이 승인 상태가 아님 |
| `ALREADY_CANCELLED` · `ALREADY_REVERSED` | 이미 취소 · 망취소됨 (진행 중 포함) |
| `AMOUNT_MISMATCH` | 금액이 원승인과 다름 |
| `MISSING_FIELD` | 필수 값 없음 (승인번호 · VAN 거래번호 등) |
| `VAN_DECLINED` | VAN이 취소를 거절 |

ERP는 사유를 화면에 보여 주기만 하고, 판단은 결제 최종 상태로 한다 (ADR-0047).

## 4. 거절된 취소 뒤 다시 취소

지금은 원승인당 취소 행이 1개라, 거절된 뒤에는 고객 재반품도 운영 취소도 못 한다. 바꾼다.

| 위치 | 지금 | 바꿈 |
|---|---|---|
| Payment `PAYMENT_CANCEL` | `UNIQUE (ORIGINAL_TRX_NO, ORIGINAL_ATTEMPT_SEQ)` | 부분 유니크 `WHERE CANCEL_STATUS IN ('PENDING', 'UNKNOWN_TIMEOUT', 'CANCELLED')` |
| Payment 취소 서비스 | 같은 원승인에 기존 취소 행이 있으면 그 상태로 재응답 | 진행 중 · 성공한 취소가 있을 때만 재응답. 거절만 있으면 새 취소 진행 |
| VAN Simulator `van_cancel` | `UNIQUE (original_pos_trx, original_attempt_seq)`, 거절도 행으로 저장 | 같은 부분 유니크. 거절된 취소만 있으면 새 취소 처리 |

- 이중 취소 방지(성공한 취소 + 망취소 ≤ 1, DESIGN.md 6장)는 그대로다. 부분 유니크가 "성공 또는 진행 중 1개"를 DB에서 보장한다.
- 거절된 취소 행은 이력으로 남는다. 합산(02)은 이미 거절 행을 "취소 없음"으로 본다.
- 이 변경이 08 부분 취소(원승인 하나에 취소 여러 건)의 밑바닥이 된다.

## 5. 저장

| 테이블 | 내용 |
|---|---|
| `OPS_REQUEST` | `ERP_REQUEST_ID`(유니크) · 종류 · 입력 JSON · 요청자 사번 · 사유 · 근거 · 처리 상태(`RECEIVED` / `WAITING_VAN` / `CLOSED`) · 결과 · reasonCode · 발급한 취소 posTrx · 일시 |
| `OPS_POS_TRX_SEQUENCE` | `(STORE_CD, EXEC_DATE)` → 마지막 거래번호 |
| `OPS_AUDIT_LOG` | 요청 ID · 종류 · 요청자 사번 · 사유 · 근거 · 검증 결과 · 실행 결과 · 대상 posTrx · `X-REQUEST-ID` · 일시. 돈을 움직인 사람의 기록 |
| `OPS_RESULT_OUTBOX` | 종료 신호 보낼 목록. 전송 · 재시도 · 격리 · 7일 보관은 02 결제 상태 아웃박스와 같은 규칙 |
| `PAYMENT_CANCEL` 컬럼 추가 | `CANCEL_KIND`(`CUSTOMER` / `OPERATION`), `OPS_REQUEST_ID` |

## 6. 종료 신호 (계약 초안)

```json
{
  "contractVersion": "1",
  "requestId": "OPR-20261126-00000123",
  "result": "DONE",
  "reasonCode": null,
  "posTrx": "1000-20261125-0003-0042-01",
  "cancelPosTrx": "1000-20261126-9999-0001-01",
  "processedAt": "2026-11-26T14:05:12+09:00"
}
```

- `result`: `DONE`(요청대로 반영) / `CLOSED_NO_CHANGE`(바꾸지 않고 종료).
- 결제 상태 메시지(02)와 같은 5분 전송으로 보낸다. 묶음은 메시지 종류별로 나눈다.

## 7. Payment가 막지 못하는 것

- "판매에 쓰인 승인인가"는 ERP 판단을 믿는다 (ADR-0040). 잘못 운영 취소하면 판매 금액과 결제 금액이 달라 ERP 대사 불일치로 올라온다 (ADR-0027).

## 8. 미정

- ERP 대기 목록 API · 종료 신호 수신 API 계약 — Retail-Platform `contracts/`에서.

## 9. 구현 작업

1. 4장 유니크 키 · 취소 서비스 변경 (Payment, VAN Simulator) + 동시성 테스트 (거절 뒤 재취소 동시 20건 → 성공 1)
2. ERP 클라이언트 · 수집 스케줄러 · `OPS_REQUEST`
3. 운영 확정 실행기 (Recovery 확정 경로 재사용, Task `RESOLVED` 처리)
4. 운영 취소 실행기 (카드 검사 없는 취소 입구, `OPS_POS_TRX_SEQUENCE`)
5. 감사 로그 · 종료 신호 아웃박스 · 전송
6. 테스트: 같은 요청 두 번 수집 → VAN 취소 1번, 운영 확정 중 Recovery가 먼저 확정(같은 결과 · 다른 결과), 운영 취소 VAN 응답 없음 → Recovery 확정 후 종료 신호, 운영 취소 posTrx가 VAN 형식 검증 통과
