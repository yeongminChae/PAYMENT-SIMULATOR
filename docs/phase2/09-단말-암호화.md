# 09. 단말 암호화

- 상태: 결정
- 날짜: 2026-11-28
- 플랫폼 근거: ADR-0006 (2단계), ADR-0050 (Retail-Platform)
- 표현 원칙: "PCI DSS 준수"라고 쓰지 않는다. **"PCI DSS 원칙을 참고한 카드 데이터 보호 설계"**로 쓴다 (ADR-0006).

## 요점

- **카드 리더가 카드번호를 읽자마자 Payment 공개키로 암호화한다.** POS 클라이언트 · 점포 서버는 암호문 + BIN만 중계하고 키가 없다. 복호화는 Payment만 한다.
- **암호 방식:** 매번 새 AES-256 키로 카드 데이터를 암호화(AES-GCM)하고, 그 AES 키를 Payment RSA 공개키로 감싼다(RSA-OAEP-256).
- **개인키:** 비밀번호로 잠긴 PKCS#12 키스토어 파일에 키 ID별로 둔다. 교체 중에는 이전 키와 새 키를 함께 받는다.
- **리더:** PAYMENT-SIMULATOR의 작은 프로그램 `card-reader-simulator`가 POS PC에서 돌며 카드를 읽고 봉투를 만든다. POS 화면은 카드번호를 모르고 봉투만 받는다 (5장).

```text
카드 리더 시뮬레이터 ─ 읽자마자 암호화
     └ 봉투(암호문 + BIN8 + 키 ID) ─▶ POS 클라이언트 ─▶ 점포 서버 ─▶ Payment ─ 복호화 ─▶ VAN
                                      (키 없음, 열 수 없음)
```

| 시스템 | 카드번호 | 보안 범위 (ADR-0006) |
|---|---|---|
| 카드 리더 시뮬레이터 | 읽자마자 암호화 | 포함 |
| POS 클라이언트 · 점포 서버 | 봉투만 중계, 키 없음 | 제외 (목표) |
| Payment Server | 복호화 · fingerprint · VAN 전문 | 포함 |

## 1. 봉투 형식 (`encryptedCard`, v1)

```json
{
  "v": 1,
  "kid": "card-2026-11",
  "alg": "RSA-OAEP-256+A256GCM",
  "ek":  "<RSA-OAEP로 감싼 AES 키, base64url>",
  "iv":  "<12바이트, base64url>",
  "ct":  "<AES-GCM 암호문 + 태그, base64url>",
  "bin8": "53275012",
  "nonce": "<16바이트 난수, base64url>",
  "issuedAt": "2026-11-28T10:15:30+09:00"
}
```

- **평문** (암호문 안): `{"pan": "...", "expiryYyMm": "..."}`.
- **AAD** (암호문에 묶이지만 평문으로 보이는 값): `v` · `kid` · `bin8` · `nonce` · `issuedAt`. 중간에서 BIN · 시각을 바꾸면 복호화가 실패한다.
- 복호화한 PAN의 앞 8자리가 `bin8`과 다르면 거부한다.
- POS · 점포 서버는 `bin8`만 읽을 수 있다. 끝 4자리 · 마스킹 번호는 Payment 승인 응답으로 받는다 (지금처럼).
- 형식은 언어와 무관하게 문서로 고정한다. POS 클라이언트 기술이 Java가 아니면 이 문서대로 구현한다.

## 2. Payment 복호화 규칙

| 검사 | 실패 코드 |
|---|---|
| 지원하는 `v` · `alg`, 알고 있는 `kid` | `CARD_KEY_UNKNOWN` |
| `issuedAt`이 지금 ± 5분 안 | `CARD_ENVELOPE_EXPIRED` |
| 복호화 · GCM 태그 검증 성공 | `CARD_DECRYPT_FAILED` |
| PAN 앞 8자리 = `bin8`, 카드 형식(길이 · Luhn · 유효기간) | `INVALID_CARD` |
| 재전송 검사 (2.1) | `CARD_ENVELOPE_REPLAYED` |

- 실패 응답 · 로그에는 코드만 남긴다. 암호문 · 평문 · 예외 원문(`cause` 메시지)을 남기지 않는다.
- 복호화한 PAN은 요청 처리 동안 메모리에서만 쓴다. `byte[]` · `char[]`로 다루고 끝나면 0으로 덮는다 (JVM 특성상 완전 삭제는 보장 못 함 — 한계로 적음).
- 복호화 뒤에는 지금과 같다: BIN8 · 끝 4자리 · HMAC fingerprint 저장, 원문 저장 금지 (ADR-0006 1단계).

### 2.1 재전송 방지

- `nonce`는 처음 쓰일 때 `CARD_ENVELOPE_NONCE`에 **posTrx와 함께** 저장한다 (10분 뒤 삭제).
- 같은 `nonce` + **같은 posTrx** → 허용. 결과 불명 뒤 같은 요청을 다시 보내는 멱등 재요청이다.
- 같은 `nonce` + **다른 posTrx** → `CARD_ENVELOPE_REPLAYED`. 가로챈 봉투를 다른 결제에 쓰는 것을 막는다.
- 멱등 판단("같은 내용인가")은 봉투가 아니라 **복호화한 카드의 fingerprint**로 한다. 카드를 다시 읽으면 봉투가 매번 달라지기 때문이다.

## 3. 키

### 3.1 보관

- PKCS#12 키스토어 파일, 항목 별칭 = `kid`. 경로는 `payment.card.keystore.path`, 비밀번호는 환경변수 `PAYMENT_CARD_KEYSTORE_PASSWORD`.
- 설정: `payment.card.active-kid`(새 봉투에 쓸 키), `payment.card.accepted-kids`(받는 키 목록).
- 키스토어 파일과 비밀번호는 저장소에 넣지 않는다. 로컬 · 테스트는 실행 시 만드는 키를 쓴다.
- **한계:** 개인키가 Payment 서버 파일에 있다. 실제 운영은 KMS · HSM · Vault로 옮긴다 (확장, ADR-0006 "설정 파일 키 쌍으로 두고 한계로 명시").

### 3.2 공개키 배포

- Payment가 `GET /api/v1/card-keys`로 공개키를 준다: `[{kid, publicKey(SPKI, base64), notAfter, active}]`.
- 점포 서버가 받아 캐시하고(점포 서버 → Payment, 요청 방향 원칙 유지), 카드 리더 시뮬레이터에 내려준다. 점포 서버는 하루 1회와 기동 시 갱신한다.
- 공개키는 비밀이 아니다. 다만 바꿔치기를 막기 위해 점포 서버 → Payment 구간은 HTTPS로 받는다.

### 3.3 교체

```text
① 새 키 추가        accepted = [old, new], active = old, 공개키 목록에 new 노출
② 1일 뒤 전환        active = new (점포 서버가 갱신할 시간)
③ 다시 1일 뒤 폐기   accepted = [new]  (old 봉투가 남아 있을 수 있는 최대 시간: 2.1의 ±5분 + 여유)
```

- 교체 주기는 1년 (설정값). 유출이 의심되면 즉시 ①~③을 몇 시간 안에 진행한다.

## 4. API 변경

- 승인 · 취소(고객 반품 카드 확인) 요청에 `encryptedCard`를 추가한다. 지금의 `card`(평문) · `cardNo`와 **둘 중 하나**만 받는다.
- **전환:** `payment.card.plaintext-input.enabled`(기본 `true`). POS 화면이 카드 리더 시뮬레이터로 옮긴 뒤 플랫폼 실행 환경에서 `false`로 끈다. 꺼지면 평문 입력은 `PLAINTEXT_CARD_NOT_ALLOWED`로 거부한다.
- 운영 취소(04)는 카드가 없으므로 변경 없다.

## 5. `card-reader-simulator` (카드 리더 시뮬레이터)

현업 구조를 작게 흉내 낸다 (가정): POS 화면은 카드번호를 받지 않고, 같은 PC의 단말 연동 프로그램에 "이 금액 카드 읽어 줘"를 요청해 암호화된 결과만 받는다.

```text
POS 화면 (브라우저)
   │ ① POST http://localhost:7070/read  {amount, testCard: "VISA_OK"}
   ▼
card-reader-simulator (POS PC에서 도는 작은 프로그램)
   │ ② 테스트 카드 목록에서 카드를 꺼내 봉투 생성 (1장 형식)
   ▼
POS 화면 ─ ③ 봉투만 받음 ─▶ 점포 서버 ─▶ Payment
```

- **POS 화면은 카드번호를 모른다.** 화면은 테스트 카드 이름만 고르고, 카드번호는 시뮬레이터의 테스트 카드 목록(설정 파일)에만 있다.
- **작게:** PAYMENT-SIMULATOR의 모듈 하나. Spring 없이 JDK 내장 HTTP 서버.
  - `GET /health`
  - `GET /cards` — 테스트 카드 이름 · 브랜드 · 시나리오 설명 (번호 없음)
  - `POST /read` — `{amount, testCard}` → 봉투(`encryptedCard`)
- **공개키:** 기동 시와 하루 1회 점포 서버에서 받는다 (3.2). 받지 못하면 `/read`가 `KEY_NOT_READY`.
- **봉투 생성 코드**는 Payment 테스트와 공유한다 (같은 형식을 Payment 종단 테스트에서도 만든다).
- PAN을 로그 · 예외 · `toString`에 남기지 않는다.
- 브라우저에서 `localhost`를 부르므로 CORS 허용(점포 서버 화면 주소만)이 필요하다. Chrome은 사설망 접근 확인 헤더(`Access-Control-Allow-Private-Network`)를 요구할 수 있다.
- 실제 결제 단말은 보안인증 IC 단말기가 읽는 시점에 암호화해 VAN으로 보낸다 (ADR-0006 맥락). 실제 단말이 BIN을 평문으로 함께 넘기는지, 연동 프로그램의 실제 인터페이스는 VAN · 제조사마다 다르다 (가정).

## 6. 범위 밖

- Payment → VAN TCP 구간의 PAN 보호. 실제로는 VAN 규격의 구간 암호화가 있다고 본다 (가정). 시뮬레이터는 평문 PAN을 보낸다 (지금과 같음). 미정.

## 7. 증명할 것 (테스트)

ADR-0006 1단계 테스트를 이어서 넓힌다.

- **종단 테스트:** 카드 리더 시뮬레이터로 만든 봉투 → (가짜) 점포 서버 → Payment 승인. 점포 서버 쪽 요청 로그 · 저장 데이터 어디에도 PAN이 없다. Payment DB · 로그 · 응답에도 PAN이 없다.
- 봉투의 `bin8`을 바꾸면 `CARD_DECRYPT_FAILED`.
- 같은 봉투 + 같은 posTrx 재요청 → 멱등 재응답. 다른 posTrx → `CARD_ENVELOPE_REPLAYED`.
- 6분 전 봉투 → `CARD_ENVELOPE_EXPIRED`.
- 키 교체 ①~③ 동안 old · new 봉투가 각각 허용 · 거부되는 시점.
- 평문 입력 끄면 `PLAINTEXT_CARD_NOT_ALLOWED`.
