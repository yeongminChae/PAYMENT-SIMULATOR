# 06. 가맹점 ID · 터미널 ID · 교차 취소

- 상태: 결정
- 날짜: 2026-11-27
- 플랫폼 근거: ADR-0031, ADR-0040, ADR-0047, ADR-0048 (Retail-Platform)
- 해소하는 차이: D15 (`00-플랫폼-차이.md`)

## 요점

- **터미널 ID는 POS마다 하나, 터미널은 한 가맹점에 속한다. v1은 점포 하나 = 가맹점 하나.** 둘 다 카드사 · VAN이 발급한 번호다 (가정). 원본은 ERP.
- **Payment가 posTrx의 점포 · POS로 직접 찾는다.** POS는 이 값을 보내지 않는다. 연결표는 Payment가 ERP에서 가져온다.
- **취소는 기본적으로 같은 가맹점 · 같은 터미널에서만 된다.** 가맹점에 **교차 취소**(`crossTerminalCancelAllowed`)가 켜져 있으면 같은 가맹점의 등록된 사용 중 터미널에서도 된다. Retail-Platform 점포는 고객센터 반품 때문에 켠다.
- Payment는 **기기 유형을 보지 않는다.** "반품은 고객센터 POS에서만"은 Retail-POS이 검증한다 (ADR-0031).
- 이 정책은 실제 VAN의 교차 취소 사례를 참고한 **프로젝트 설계 정책**이며, 모든 VAN사의 공통 규격이라고 가정하지 않는다.

## 1. 개념 · 참고 사례

**일반 구조 (가정):** 국내 오프라인 카드 결제에서 가맹점 ID는 카드를 받는 사업자(가게)의 번호로 매출 정산 단위이고, 터미널 ID(TID)는 VAN이 결제 단말기마다 주는 번호다. 실제 VAN 계약 문서로 확인하지 않았다.

**교차 취소 참고 사례 (확인, 원문 미열람):** KIS정보통신 VAN 서비스 이용약관 제9조. 웹 검색 결과 요약 기준이며, 약관 원문 · 개정일은 직접 열어 확인하지 않았다.
- 단말기로 승인받은 거래는 단말기로 취소한다 (2019년 약관 PDF).
- 가맹점이 "POS 단말기 교차취소요청서"를 내면, 가맹점 안의 모든 POS 단말기에서 교차 취소가 가능하도록 설정된다.

이 프로젝트는 이 사례를 따라 "기본은 같은 터미널, 가맹점 설정으로 교차 취소 허용"으로 둔다.

## 2. 점포 · 가맹점 · 터미널 관계

```text
점포 1 ──── N 가맹점          v1 제약: 점포당 가맹점 1개
가맹점 1 ── N 터미널
터미널 1 ── 1 POS (점포 + POS 번호)
```

- **가맹점은 터미널로 정한다.** POS → 터미널 → 가맹점. 점포 → 가맹점으로 바로 찾지 않는다.
  - v1은 점포당 가맹점이 하나라 결과가 같다.
  - 카페 키오스크 · 소상공인(backlog)처럼 한 점포에 사업자가 여럿이면 점포당 가맹점 N개가 되는데, 그때도 Payment 로직은 바뀌지 않는다.
- 하나의 가맹점은 한 점포에만 속한다 (점포를 넘는 가맹점 없음).
- 운영 전용 POS(9999, ADR-0047)는 단말이 없어 터미널 ID가 없다.

### 2.1 Payment 사본

| 테이블 | 키 | 값 |
|---|---|---|
| `MERCHANT` | `MERCHANT_ID` | `STORE_CD`, `CROSS_TERMINAL_CANCEL_ALLOWED`, `ACTIVE` |
| `TERMINAL` | `TERMINAL_ID` | `MERCHANT_ID`, `STORE_CD`, `POS_NO`, `ACTIVE` (`UNIQUE (STORE_CD, POS_NO)`) |

- 기기 유형은 저장하지 않는다.
- **동기화** (ADR-0048)
  - 하루 1회 전체를 받는다 (기본 03:00, 설정값).
  - 5분 운영 요청 수집 때 마지막 버전 이후 변경분을 함께 받는다.
  - ERP 연결이 안 되면 가진 사본으로 계속 처리하고, 30분 넘게 실패하면 알림 (05).

## 3. 승인

1. posTrx에서 점포 · POS를 꺼내 `TERMINAL`을 찾고, 그 터미널의 가맹점을 찾는다.
2. 터미널이 없거나 사용 중지, 가맹점이 사용 중지면 VAN 호출 없이 거부한다: `TERMINAL_NOT_REGISTERED` / `TERMINAL_INACTIVE` / `MERCHANT_INACTIVE`.
3. `PAYMENT_ATTEMPT`에 `MERCHANT_ID` · `TERMINAL_ID`(원승인 TID)를 저장한다. 승인 시점 값으로 고정된다.
4. VAN 승인 전문에 두 값을 싣는다.

## 4. 취소 · 망취소

### 4.1 고객 반품 취소

취소 posTrx의 점포 · POS로 취소 터미널을 찾은 뒤 다음 순서로 검증한다.

| # | 검사 | 실패 코드 |
|---|---|---|
| 1 | 취소 터미널이 등록 · 사용 중 | `TERMINAL_NOT_REGISTERED` / `TERMINAL_INACTIVE` |
| 2 | 취소 터미널의 가맹점 = 원승인 가맹점 | `MERCHANT_MISMATCH` |
| 3 | 취소 터미널 = 원승인 터미널, **또는** 원승인 가맹점의 `CROSS_TERMINAL_CANCEL_ALLOWED = true` | `CROSS_TERMINAL_CANCEL_NOT_ALLOWED` |
| 4 | 거래 정합성: 원승인 `APPROVED`, 성공 · 진행 중 취소 · 망취소 없음, 금액, 카드 일치(fingerprint) | 기존 코드 |

- 교차 취소 설정은 **취소 시점**의 가맹점 설정을 본다.
- `PAYMENT_CANCEL`에 `CANCEL_TERMINAL_ID`를 저장한다. 원승인 TID는 `PAYMENT_ATTEMPT.TERMINAL_ID`에 있으므로, 두 TID를 각각 기록한다.
- 고객센터 POS에서만 반품을 허용하는 것은 Retail-POS이 검증한다 (ADR-0031). Payment는 기기 유형에 의존하지 않고 가맹점 · 터미널 · 교차 취소 권한 · 거래 정합성만 본다.

### 4.2 망취소

- 같은 POS가 결과 불명 직후 보내므로 원승인과 같은 터미널이어야 한다. 위 1 · 2 · 4를 보고, 3은 "같은 터미널"만 허용한다 (교차 망취소 없음).

### 4.3 운영 취소 (ADR-0040, 0047)

- **별도 권한 경로**다. 담당자 요청(ERP) → Payment 검증(04)으로 권한을 확인하고, 교차 취소 설정과 무관하다.
- 단말이 없으므로 VAN에는 **원승인 TID**로 보낸다. `CANCEL_TERMINAL_ID`에도 원승인 TID를 적고, `CANCEL_KIND = OPERATION`으로 구분한다.

## 5. VAN Simulator

- VAN Simulator도 **독립적으로** 교차 취소 정책을 검증한다. Payment 검증을 믿지 않는다.
- 자체 가맹점 · 터미널 등록부를 가진다 (`van_merchant` · `van_terminal`, 교차 취소 설정 포함). 실제로는 VAN이 TID 발급처이므로 VAN 등록부가 원래 원본이고, ERP는 그 값을 입력해 둔 것이다 (가정). 시뮬레이터에서는 시드 데이터 · Control Plane으로 등록한다.
- 전문 v2(`protocolVersion` 2): 승인 · 취소 · 망취소에 `merchantId` · `terminalId`를 추가한다. 취소 전문의 `terminalId`는 취소 TID, 원승인 TID는 VAN 원장에서 찾는다.
- VAN 검사: 미등록 터미널, 가맹점 불일치, 교차 취소 불허 → 거절 원장 + 거절 코드. 원승인 TID와 취소 TID를 원장에 각각 저장한다.

## 6. 기존 데이터

- 이미 저장된 승인은 가맹점 · 터미널 값이 없다(NULL). 그 승인의 취소는 가맹점 · 터미널 검사를 건너뛰고 경고 로그를 남긴다. 새 승인부터는 필수다.

## 7. 나중에 이어지는 것

- 매입 · 정산(07)은 가맹점 ID별로 묶는다.
- 카페 키오스크 · 소상공인은 점포당 가맹점 N개로 v1 제약만 풀면 된다. 가맹점 ID가 매출 귀속 키가 된다.

## 8. 구현 작업

1. `MERCHANT` · `TERMINAL` 테이블, ERP 동기화 (일 1회 전체, 5분 변경분)
2. 승인 입구 검사, `PAYMENT_ATTEMPT` 컬럼 추가
3. 취소 검사(4.1 표 순서) · `CANCEL_TERMINAL_ID`, 망취소 같은 터미널 검사, 운영 취소 원승인 TID
4. VAN 전문 v2, VAN Simulator 등록부 · 독립 검사 · TID 두 개 저장
5. 테스트
   - 교차 취소 꺼진 가맹점: 같은 TID 취소 성공, 다른 TID `CROSS_TERMINAL_CANCEL_NOT_ALLOWED`
   - 교차 취소 켜진 가맹점: 고객센터 POS 취소 성공, 두 TID가 각각 기록됨
   - 다른 점포 POS 취소: `MERCHANT_MISMATCH`
   - Payment 검사를 우회한 전문: VAN이 독립적으로 거절
   - 운영 취소: 교차 취소 설정과 무관하게 원승인 TID로 성공
