# 플랫폼 결정과 현재 코드의 차이

- 기준일: 2026-11-25
- 플랫폼 기준: Retail-Platform `main` — `docs/summary.md`, `docs/backlog.md`, ADR-0002 · 0006 · 0021 · 0025 · 0026 · 0040 · 0043 · 0044 (+ 필요 시 0003 · 0017 · 0036 · 0042)
- 코드 기준: PAYMENT-SIMULATOR `main` `2e05320`

2단계 설계의 출발점이다. 각 항목을 어느 설계 문서에서 다루는지 오른쪽에 적는다.

## 1. 플랫폼 결정과 코드가 어긋나는 곳

| # | 플랫폼 결정 | 현재 코드 | 영향 | 다룰 곳 |
|---|---|---|---|---|
| D1 | posTrx = `거래번호-결제순번` (ADR-0002). 거래번호 = `점포-영업일-POS-순번` | 승인 DTO `@Pattern ^\d{4}-\d{8}-\d{4}-\d{4}$`, VAN Simulator `PosTrxProtocolValidator`도 같은 패턴으로 승인 · 취소 · 망취소 전문을 검증 | 새 형식 posTrx로는 승인이 **400**, VAN도 거부. 연동 불가 | 01 |
| D2 | `/pos-trx/issue`는 이 연동에서 쓰지 않음 (ADR-0002) | `/api/v1/pos-trx/issue` · `/eot`, `POS_TRX_SEQUENCE` 존재 | 쓰이지 않는 발급 기능이 남음 | 01 |
| D3 | ADR-0025 맥락: "결과 불명 → 망취소 → **같은 posTrx로 재결제**" | 같은 posTrx의 새 시도(`attemptSeq` 증가)는 직전 시도가 `DECLINED`일 때만 허용. `UNKNOWN_TIMEOUT`(망취소 후 포함)이면 같은 내용은 저장된 결과 재응답, 다른 내용은 `POS_TRX_ALREADY_USED` | 망취소 후 재결제는 같은 posTrx로 할 수 없음 → 새 결제순번이 필요 | 01 |
| D4 | 운영 취소: 확정 승인이고 **성공한** 취소 · 망취소가 없는 건 (ADR-0040) | `PAYMENT_CANCEL`에 `UNIQUE (ORIGINAL_TRX_NO, ORIGINAL_ATTEMPT_SEQ)` — 원승인당 취소 행 1개. 거절된 취소(`CANCEL_DECLINED`)가 있어도 새 취소는 기존 행을 재응답 | 반품 취소가 거절된 승인은 운영 취소로도 되돌릴 수 없음. 부분 취소도 구조상 불가 | 04, 08 |
| D5 | 운영 취소는 카드 불필요, 저장된 원승인 정보로 VAN에 보냄 (ADR-0040) | `/cancel`은 `cardNo` 필수 + fingerprint 비교(`CARD_MISMATCH`) | 카드 없는 취소 경로가 없음 | 04 |
| D6 | 운영 취소는 Payment가 실행 — 취소 거래의 posTrx를 누가 만드나 | 취소 식별자는 POS가 보낸 `posTrx`(취소 거래번호). VAN도 취소 거래번호 형식을 검증 | 운영 취소용 취소 거래번호 규칙이 없음 | 04 |
| D7 | posTrx별 합산 상태(빠짐 · 안 빠짐 · 미확정, 빠진 금액 · 승인 목록, 미확정 건, `MANUAL_REVIEW` 여부, 버전)를 아웃박스로 5분마다 전송 (ADR-0025, 0043) | 합산 로직 · 아웃박스 · 전송 스케줄러 · 버전 없음 | 신규 | 02 |
| D8 | 운영 조회: posTrx 현재 상태 읽기 전용, ADR-0025 합산 기준 (ADR-0026) | `/inquiry`는 VAN에 묻는 결과 조회. 저장 상태만 읽는 API 없음 | 신규 | 03 |
| D9 | 운영 확정: `MANUAL_REVIEW` 건을 담당자가 확인한 결과로 확정 (ADR-0040) | `MANUAL_REVIEW`는 재대기(requeue)만. 수기 확정(Force Resolve) 없음 (DESIGN.md 11장) | 신규 | 04 |
| D10 | 운영 요청을 5분마다 ERP에서 가져와 검증 · 실행, 감사 로그 (ADR-0040) | ERP 클라이언트 · 요청 수집 · 운영 감사 로그 없음 (`PAYMENT_EVENT_LOG`는 거래 이벤트용) | 신규 | 04 |
| D11 | 플랫폼 실행 환경에서 Recovery 스케줄러를 켬 (ADR-0021), 내부 1분 (ADR-0042) | `payment.recovery.schedule.enabled` 기본 `false`. Recovery · 관리 API는 `postgres` 프로파일에서만 존재. 기본 프로파일은 SQLite | 플랫폼이 어떤 프로파일로 띄우는지에 따라 Recovery가 아예 없음 | 05 |
| D12 | 알림 1채널(예: Slack 웹훅), Prometheus 지표, 아웃박스 30분 · 격리 즉시 알림 (standards.md, ADR-0043) | `MANUAL_REVIEW` 알림은 구조화 로그만. Actuator · Micrometer 의존성 없음 | 신규 | 05 |
| D13 | Payment 운영 조회 · 수기 조치는 전산 담당자만 (ADR-0036) | `/api/admin/**`에 인증 · 권한 없음 | 운영 조회를 열면 누구나 결제 상태를 읽음 | 03 |
| D14 | Recovery 스케줄러 로그의 추적 ID는 이 레포에서 정함 (ADR-0017) | HTTP 요청만 `X-REQUEST-ID` → MDC. 스케줄러 · 배치 실행에는 requestId 없음 | 백그라운드 작업 로그를 묶을 키 없음 | 05 |
| D15 | 가맹점 ID · 터미널 ID 기록 · 취소 시 검증 (backlog, TBD) | 승인 요청 · 저장 · VAN 전문 어디에도 없음 | 신규 | 06 |
| D16 | 매입 · 정산: 매입은 Payment, 매입 전 ERP에 "매입 제외 목록" 요청 (backlog) | 없음 (DESIGN.md 11장) | 확장 | 07 |
| D17 | 부분 취소 (backlog 확장 1순위, 부분 반품의 전제) | 없음. D4의 유니크 키가 구조적으로 막음 | 확장 | 08 |

## 2. 이미 맞는 것 (변경 불필요)

| 플랫폼 결정 | 코드 |
|---|---|
| 추적 ID `X-REQUEST-ID`를 받으면 그대로 쓰고 응답에 돌려줌 (ADR-0017) | `RequestIdProviderImpl.HEADER = "X-REQUEST-ID"`, MDC `requestId` |
| Payment → VAN 구간은 별도 `vanRequestId` (ADR-0017) | VAN 전문 `requestId` 분리 |
| 응답 없음 = 결과 불명, 같은 요청 재전송 금지 (ADR-0003, 0021) | `UNKNOWN_TIMEOUT`, request-not-sent만 정리 후 재시도 허용 |
| 망취소는 원승인 `UNKNOWN_TIMEOUT`일 때만, 원승인 상태는 바꾸지 않음 (ADR-0021 맥락) | `PaymentReversalServiceImpl`, 원장 분리 |
| 취소 + 망취소 성공은 원승인당 최대 1 | DESIGN.md 6장 불변식 |
| 카드번호 원문 저장 금지, BIN8 · 끝 4자리 · fingerprint (ADR-0006 1단계) | `PAYMENT_ATTEMPT`, `CardFingerprintPolicy` |
| 고객 반품은 카드 필수 (ADR-0040) | `/cancel` `cardNo` 필수 + fingerprint 비교 |
| Recovery는 VAN에 조회만, 확정 못 하면 `MANUAL_REVIEW` (ADR-0021) | DESIGN.md 7장 |
| Recovery 주기 1분 (ADR-0042) | `fixed-delay-ms` 기본 60000 |

## 3. 플랫폼 문서의 맥락 서술 중 코드와 다른 것

ADR 본문(결정)은 아니고 맥락 서술이라 ADR 변경 대상은 아니다. 01에서 정한 뒤 필요하면 Retail-Platform에 기록한다.

- ADR-0025 맥락의 "같은 posTrx로 재결제" — D3. 현재 코드에서는 성립하지 않는다.
