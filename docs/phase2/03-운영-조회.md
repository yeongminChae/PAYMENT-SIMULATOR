# 03. 운영 조회

- 상태: 결정
- 날짜: 2026-11-26
- 플랫폼 근거: ADR-0026, ADR-0036, ADR-0045, ADR-0046 (Retail-Platform)
- 해소하는 차이: D8 · D13 (`00-플랫폼-차이.md`)

## 1. 용도와 원칙

- 고객 문의("두 번 결제됐어요", "환불이 안 됐어요")에 전산 담당자가 **지금 상태**를 바로 확인한다. ERP 화면은 최대 5분 늦다 (ADR-0026).
- **읽기만 한다.** 상태를 바꾸는 수기 조치는 ERP 운영 요청으로 한다 (ADR-0040, 04).
- **VAN에 묻지 않는다.** Payment에 저장된 사실을 보여 준다. VAN 확인이 필요한 결과 불명 건은 Recovery가 처리한다.
- 판정은 02의 합산기(`PaymentTrxStatusCalculator`)를 **원장에서 바로** 돌려 낸다. ERP에 마지막으로 보낸 버전도 함께 보여 줘, ERP 화면과 다른 이유(전송 대기)를 설명할 수 있게 한다.

## 2. 찾는 방법

고객이 가진 것에서 출발한다.

| 고객이 가진 것 | 조회 | 결과 |
|---|---|---|
| 영수증 | `receiptNo` (`점포-발행일-POS-거래번호`, ADR-0046) | 후보 거래 키 최대 2개의 posTrx 목록 |
| 거래 키 (ERP · POS 화면) | `trxKey` (`점포-영업일-POS-거래번호`) | 그 거래의 posTrx 전부 (`-01`, `-02` …) |
| posTrx | `posTrx` | 한 건 상세 |
| 카드사 알림 문자 | `approvalNo` + `approvalDate` | 그 날(±1일) 해당 승인번호의 승인 목록 |

### 2.1 영수증번호로 찾기

- 영수증번호의 날짜는 **발행일(달력)**, 거래 키의 날짜는 **영업일**이다. 자정이 지나 점포 마감 전에 판매하면 둘이 다르다 (ADR-0046).
- 그래서 Payment는 `점포-발행일-POS-거래번호`를 받아 영업일 후보 **발행일 · 발행일 전날** 두 개로 거래 키를 만들어 찾는다.
- 둘 다 있으면 둘 다 돌려준다. 담당자가 승인 일시 · 금액으로 고른다. 전날 영업일의 같은 번호는 대개 그 시각이 자정 전후라 쉽게 구분된다.
- Payment는 영수증번호를 저장하지 않는다. 형식만 안다 (ADR-0046).

### 2.2 승인번호로 찾기

- 승인번호는 전역 유일이 아닐 수 있으므로(가정) 날짜를 함께 받는다. `approvalDate` 하루 ±1일 범위의 `APPROVED` 승인에서 찾는다.
- 취소 승인번호(`CANCEL_APPROVAL_NO`)로도 찾는다. 고객이 받은 취소 문자에도 승인번호가 있다.

## 3. API

경로 `/api/ops/v1/payments`. 모두 `GET`.

| 경로 | 파라미터 |
|---|---|
| `/pos-trx/{posTrx}` | — |
| `/search` | `receiptNo` 또는 `trxKey` 또는 `approvalNo` + `approvalDate` 중 하나 |

`/search`는 posTrx 요약 목록, `/pos-trx/{posTrx}`는 상세를 돌려준다.

### 3.1 상세 응답 (예)

```json
{
  "posTrx": "1000-20261126-0001-0199-01",
  "status": "UNRESOLVED",
  "statusLabel": "미확정 — 결과 확인 중인 거래가 있음",
  "chargedAmount": 0,
  "doubleCharged": false,
  "approvals": [
    { "attemptSeq": 1, "finalStatus": "UNKNOWN_TIMEOUT", "verdict": "UNRESOLVED",
      "amount": 15000, "approvalNo": null, "maskedCardNo": "53275012******1234",
      "cardBrand": "MASTER", "createdAt": "2026-11-26T19:02:11+09:00" }
  ],
  "cancels": [],
  "reversals": [
    { "reversalPosTrx": "1000-20261126-0001-0199-01", "originalAttemptSeq": 1,
      "reversalStatus": "PENDING", "createdAt": "2026-11-26T19:02:20+09:00" }
  ],
  "recoveryTasks": [
    { "taskId": 812, "targetType": "REVERSAL", "recoveryStatus": "RETRY_WAIT",
      "retryCount": 2, "nextRetryAt": "2026-11-26T19:10:00+09:00", "lastError": "VAN_INQUIRY_TIMEOUT" }
  ],
  "erpSync": { "currentVersion": 2, "sentVersion": 1, "sendStatus": "PENDING", "lastSentAt": "2026-11-26T19:05:00+09:00" },
  "sameTrxKey": ["1000-20261126-0001-0199-02"]
}
```

- `status` · `verdict`는 02 1장의 판정이다. `statusLabel`은 담당자가 고객에게 설명할 때 쓰는 한국어 문구다.
  - `CHARGED` "빠짐 — 고객 카드에 결제가 남아 있음"
  - `NOT_CHARGED` "안 빠짐 — 승인 없음 또는 취소 · 망취소 완료"
  - `UNRESOLVED` "미확정 — 결과 확인 중인 거래가 있음"
- `doubleCharged`: 빠진 승인 2건 이상 (ADR-0025).
- `cancels[].kind`: `CUSTOMER`(고객 반품) / `OPERATION`(운영 취소, 04).
- `sameTrxKey`: 같은 거래 키의 다른 posTrx. 망취소 뒤 재결제(ADR-0045)를 한눈에 본다.
- `erpSync`: `currentVersion > sentVersion`이면 "ERP에는 아직 반영 전(최대 5분)".
- 카드는 마스킹 번호 · 브랜드만. 카드번호 원문 · fingerprint는 내보내지 않는다 (ADR-0006).

### 3.2 고객 문의별로 보는 법

| 문의 | 보는 곳 | 안내 |
|---|---|---|
| "두 번 결제됐어요" | `doubleCharged`, `sameTrxKey`의 각 posTrx 상태 | 같은 거래 키의 `-01`이 빠짐이고 `-02`도 빠짐이면 하나는 판매에 쓰이지 않은 승인 → ERP 운영 취소 대상 (ERP가 판단, ADR-0040) |
| "결제 안 됐는데 문자가 왔어요" | 그 posTrx가 빠짐인지, 판매에 쓰였는지(ERP) | 빠짐 + 판매 없음 → 운영 취소 대상 |
| "환불이 안 됐어요" | 원승인 posTrx의 `cancels[]` | `CANCELLED`면 카드사 반영 대기(가정: 카드사마다 수일), `CANCEL_DECLINED`면 04 |
| "결제 확인 중이라던데요" | `UNRESOLVED`, `recoveryTasks` | Recovery 진행 중 / `MANUAL_REVIEW`면 VAN · 카드사 확인 후 ERP 운영 확정 (ADR-0040) |

## 4. 접근 통제

v1은 최소로 한다. 수기 조치의 권한 · 감사는 ERP 운영 요청(ADR-0036, 0040)이 맡고, Payment 운영 API는 **읽기 · 재대기 · 재전송**뿐이기 때문이다.

- `/api/ops/**`와 기존 `/api/admin/recovery/**`에 필터 하나를 둔다.
  - `X-OPS-KEY` 헤더 = 환경변수 `PAYMENT_OPS_API_KEY`. 없거나 다르면 401. 키가 설정되지 않았으면 운영 API를 열지 않는다(기동 시 경고, 모든 요청 503).
  - `X-OPERATOR-ID` 헤더(사번) 필수. 없으면 400. 값은 검증하지 않고 기록한다.
- 조회 기록 `OPS_ACCESS_LOG`: 사번 · API · 조회 키 · 결과 건수 · `X-REQUEST-ID` · 일시. 결제 정보를 누가 봤는지 남긴다.
- 로컬: `export PAYMENT_OPS_API_KEY=local-dev-key` 후 curl로 호출. 테스트: MockMvc로 키 없음 · 틀림 · 사번 없음 · 정상.
- **알려진 한계:** 키를 아는 사람은 다른 사번을 적을 수 있다. 운영 API는 본사 내부망에만 노출하는 배포 전제로 둔다. 사람 단위 인증(ERP 발급 토큰 등)은 확장으로 둔다.

## 5. 저장 · 성능

- 인덱스: `PAYMENT_ATTEMPT (APPROVAL_NO)`, `PAYMENT_CANCEL (CANCEL_APPROVAL_NO)`, 거래 키 접두 검색용 `PAYMENT_ATTEMPT (POS_TRX text_pattern_ops)` (PostgreSQL).
- 거래 키 검색은 `POS_TRX LIKE '{trxKey}-%'`.
- SQLite · PostgreSQL 두 프로파일 모두에서 동작한다 (읽기 전용이라 Recovery 프로파일 제약과 무관).

## 6. 구현 작업

1. 운영 키 필터 + `OPS_ACCESS_LOG`
2. 조회 서비스: 원장 · Recovery Task · `PAYMENT_TRX_STATUS` · 아웃박스를 읽어 상세 조립, 합산은 02 합산기 재사용
3. 검색: `receiptNo`(영업일 후보 2개) · `trxKey` · `approvalNo + approvalDate`
4. 인덱스
5. 테스트: 영수증 자정 이후 판매 → 전날 영업일 거래 키로 찾음, 같은 거래 키 `-01` 망취소 · `-02` 승인, 이중 결제 표시, ERP 미반영 버전 표시, 응답에 카드번호 원문 · fingerprint 없음
